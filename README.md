# AQAP API

واجهة برمجية (FastAPI) لمنصة إدارة الجودة والاعتماد الأكاديمي، مبنية فوق مخطط `db/schema.sql`.

## التشغيل على GitHub (Codespaces)

1. ارفع المشروع إلى مستودع GitHub (يُفضّل **خاص**).
2. من صفحة المستودع: **Code ← Codespaces ← Create codespace on main**.
3. تُبنى البيئة تلقائياً (قاعدة بيانات + LibreOffice + بيانات العرض) وتُفتح المنصة على المنفذ 8000.
4. ادخل بأحد حسابات العرض: `dean@ynb` · `auditor@ynb` · `hod.cs@ynb` · `coord.cs@ynb`.

لاستخدام النموذج الرسمي بدل بيانات العرض: ضع الملف في `templates/model.xlsb` داخل الـ Codespace ثم احذف القاعدة وأعد
`bash scripts/dev_setup.sh` (الملف مستثنى من git عمداً). المنفذ خاص افتراضياً ويتطلب حساب GitHub؛ لا تجعله عاماً
لأن الدخول في وضع التطوير بالبريد فقط. وكل دفع للمستودع يشغّل الاختبارات تلقائياً (GitHub Actions).

## التشغيل على خادم

```bash
cp .env.example .env        # عدّل كلمات المرور والسر
docker compose up -d --build
# التوثيق التفاعلي: http://localhost:8000/docs
```

بعد أول تشغيل، استورد النموذج الرسمي (يتطلب `pip install pyxlsb`):

```bash
# 1) معاينة دون كتابة
python scripts/import_xlsb.py نموذج_العمل.xlsb --dry-run
# 2) الإطار فقط: 6 معايير، 18 معياراً فرعياً، 48 متطلباً بنصوصها الرسمية
python scripts/import_xlsb.py نموذج_العمل.xlsb --dsn postgresql://aqap:aqap@localhost:5432/aqap
# 3) + الأقسام وأعداد المدربين والمتدربين من ورقة بيانات المنشأة
python scripts/import_xlsb.py نموذج_العمل.xlsb --dsn ... --institution-id 1
# 4) + التقديرات المعبأة (ذاتي/خارجي/توصيات/ملاءمة) إلى دورة قائمة
python scripts/import_xlsb.py نموذج_العمل.xlsb --dsn ... --institution-id 1 --cycle-id 1 --actor-id <وكيل الجودة>
```

الاستيراد آمن للتكرار (يحدّث ولا يكرر) ويجري في معاملة واحدة. ملاحظات المطابقة مع الملف:
- المتطلبات الموسومة بـ`*` و`**` تُحفظ بنص نظيف، وشرط الانطباق يظهر كإرشاد تحت المتطلب.
- "منطبق" في التقييم الخارجي (تأكيد «لا ينطبق») يُحفظ «لا ينطبق»، و"غير منطبق" يُحفظ «غير متحقق».
- ما له تقييم خارجي يدخل حالة «مُدقَّق» بانتظار اعتماد وكيل الجودة، والباقي يبقى مسودة لمراجعة القسم.
- روابط الشواهد (OneDrive) وأوراق خطط التحسين واللجان لا تُستورد في هذه النسخة.

ثم أضف المستخدمين وأدوارهم.

## التصدير إلى القالب الرسمي

زر «تصدير النموذج الرسمي (Excel)» في لوحة المؤشرات (أو `GET /api/v1/cycles/{id}/export/official`) يعبّئ ملف
«نموذج العمل الشامل» نفسه: بيانات المنشأة والأقسام، والتقييم الذاتي وحكم المقيّم والتوصيات في أوراق المعايير،
وخطط التحسين في أوراق «تحسين قسم» بالترتيب الذي تولده صيغ القالب. يُحفظ بصيغة .xlsx (لا توجد أداة غير Excel تكتب .xlsb)،
مع إبقاء القوائم المنسدلة والتنسيق والرسوم، ويعيد Excel حساب الصيغ عند الفتح.

- ضع القالب في `templates/model.xlsb` (مركّب في الحاوية) واضبط `AQAP_OFFICIAL_TEMPLATE`.
- التوليد يستغرق نحو دقيقة لأن القالب ثقيل الصيغ.
- اختبار التطابق مع القالب (بطيء): `AQAP_TEST_LIBREOFFICE=1 AQAP_TEST_XLSB=<الملف> pytest -k export`
  يعيد حساب القالب ويتحقق أن ترتيب خطط التحسين ونسب «%المتحقق» لكل قسم × معيار مطابقة لحساب المنصة.

## وحدة المحاضر

نموذج رقمي موحّد للمتطلبات الثلاثة عشر التي شاهدها «محضر اجتماع» (1-1-1، 1-2-1، 1-3-1، 2-1-2، 2-2-3، 2-2-8، 3-1-1،
3-2-1، 3-2-3، 3-2-4، 3-3-1، 4-1-1، 4-3-2)، بلا أي بيانات خاصة بقسم: محاور مقترحة قابلة للتعديل، وتوصيات بمسؤول وفترة تنفيذ،
وحضور (أعضاء القسم المسجلون يُضافون تلقائياً ويؤكدون حضورهم إلكترونياً)، واعتماد رئيس القسم.

- المسار: مسودة ← مرفوع ← معتمد (أو معاد بسبب). وكيل الجودة وحده يعيد فتح محضر معتمد.
- عند الاعتماد يُولَّد PDF عربي (WeasyPrint) بالتاريخين الهجري والميلادي، ويُحفظ في بنك شواهد القسم ويُربط بالمتطلب
  إن كان تقديره لدى القسم. ورقم الاجتماع يُرقَّم تلقائياً لكل متطلب وقسم ودورة.
- متابعة التوصيات بعد الاعتماد: مُنفذ / مُنفذ جزئي / لم يُنفذ مع المعوقات والحلول، ونسبة التنفيذ = (مُنفذ + ½ جزئي) ÷ الإجمالي
  كما في نموذج المتابعة. «أرشفة نسخة المتابعة» تضيف نسخة PDF جديدة للشاهد نفسه.
- **الشواهد والتقارير الداعمة**: يُرفق بالمحضر ملف (يُرفع إلى بنك شواهد القسم) أو رابط أو شاهد موجود في البنك، مثل كشف الحضور
  الموقّع وصور الاجتماع والتقارير التي نوقشت. تُضاف في المسودة أو بعد الإعادة أو بعد الاعتماد (شواهد المتابعة)، ولا تُضاف والمحضر
  بانتظار قرار رئيس القسم، وتُزال قبل الاعتماد فقط (تبقى في البنك). عند الاعتماد تُربط بالمتطلب مع PDF المحضر، وما يُضاف بعده
  يُربط فوراً، وتظهر في جدول «الشواهد والتقارير الداعمة» داخل PDF. القاعدة تمنع إرفاق شاهد من قسم آخر أو شاهد سري.
- **جاهزية المحضر**: قائمة تحقق حيّة قبل الرفع (التاريخ، المحاور، التوصيات ومسؤولوها، الحضور، الشواهد الداعمة).
- **قاعدة قائمة**: إن أُنشئت قاعدتك قبل وحدة الشواهد الداعمة، طبّق الترحيل مرة واحدة (آمن للتكرار):
  `psql "$AQAP_DATABASE_URL" -v ON_ERROR_STOP=1 -f db/migrations/001_minutes_attachments.sql`

## الخطط والتقارير (محرّك النماذج)

كل متطلب شاهده «خطة» أو «تقرير» له نموذج إلكتروني بنفس حقول وصيغ ملف Excel الرسمي، دون أي بيانات خاصة بقسم.
القوالب معرّفة في `app/form_templates.py` وتُزامن مع قاعدة البيانات تلقائياً عند التشغيل (إصدار جديد عند التغيير فقط)،
فإضافة نموذج جديد تعريف بيانات لا برمجة.

- **المعيار الأول (القيادة الإدارية)**: 1-1-2 خطة المبادرات، 1-2-2 تهيئة المدربين وتقييمهم، 1-2-3 الاستثمار الأمثل للموارد
  البشرية (ملخص محوري لكل تخصص)، 1-3-2 خطة تهيئة الشعب والجداول، 1-3-3 القبول السنوي والطاقة الاستيعابية، 1-3-4 مؤشرات
  عنصر الجداول التدريبية (تقدير نسبة المدربين إلى المتدربين آلياً)، 1-4-1 خطة التواصل والمشاركة، 1-4-2 سجل الشكاوى والتظلمات
  والمقترحات مع إحصائياتها لكل تخصص وللقسم. ولكل نموذج جدول «التوصيات وخطط التحسين» الموحّد.
- **المعيار الثاني (نواتج التدريب)**: 2-1-1 خطة متابعة الإرشاد، 2-1-3 تتبع المرشد لأداء المتدربين (ملخص لكل مرشد)،
  2-2-1 نتائج جودة المخرجات (السمات الشخصية واختبار التخصص)، 2-2-2 تحليل نتائج المتدربين لكل مقرر واختبار، 2-2-4 خطة الإشراف
  على التدريب التعاوني، 2-2-5 لجنة مناقشة التعاوني والإنتاجي، 2-2-6 متابعة متدربي مبادرة رافد، 2-2-7 خطة البرامج وورش العمل،
  2-2-9 خطة مقرر المشروع، 2-2-10 لجنة مناقشة نتائج المشاريع.
- **المعيار الثالث (المناهج وأدوات القياس)**: 3-1-2 مراجعة أسئلة الاختبارات بالمعايير الأحد عشر، 3-2-2 خطة مراجعة الخطط التدريبية،
  3-2-5 تكامل مدربي المقررات المشتركة، 3-3-2 توافق المحتوى مع مفردات الخطط.
- **المعيار الرابع (التدريب والموارد المساندة)**: 4-1-2 استراتيجيات التدريب، 4-1-3 ملف المدرب والمنصات الإلكترونية، 4-2-1 التجهيزات
  والمعامل، 4-2-2 طلبات تأمين التجهيزات، 4-3-1 قياس سير العملية التدريبية الأسبوعي.
  - **المعيار الخامس (البيئة التدريبية):** 5-1-1 خطة الصيانة الدورية، 5-1-2 خطة متابعة النظافة، 5-2-1 خطة الصحة والسلامة (خطط تنفيذية)، 5-1-3 تقرير كفاءة المرافق لكل مبنى (درجات 0–2 للممرات والمستودعات والقاعات، وتقييم ممتاز/متوسط/ضعيف للعنصر والمبنى).
  - **المعيار السادس (الاستدامة):** 6-2-1 متابعة إنجازات ومبادرات القسم، 6-1-1 تقرير الاستدامة (37 معيارًا فرعيًا للاعتماد المؤسسي + نتائج نظام جودة التدريب مقارنة بخط الأساس)، 6-3-1 سجل المخاطر (شدة التأثير × الاحتمالية → منخفضة/متوسطة/عالية)، 6-4-1 نتائج مؤشرات المستوى الثاني (45 مؤشرًا ثابتًا مع متوسط لكل معيار).
- **مرحلتان للبيانات**: التخطيط يُعبأ في المسودة ويُقفل بالاعتماد؛ والمتابعة (المتحقق، حالة التنفيذ، المعوقات، خطط التحسين)
  تبقى مفتوحة بعد الاعتماد طوال الدورة. القفل مفروض في قاعدة البيانات.
- **الصيغ** مطابقة لملفات Excel: نسبة المتحقق، متوسط نسبة الإنجاز = مجموع المتحقق ÷ مجموع المستهدف، نسبة التنفيذ =
  (مُنفذ + ½ جزئي) ÷ المتابَع، نسبة التحسين = (مُنفذ + ½ جزئي) ÷ التوصيات المدخلة. تُحسب حيّة في الواجهة
  (`frontend/js/formcalc.js`) وفي الخادم وPDF (`app/forms_engine.py`)، واختبار يضمن تطابقهما.
- **الاعتماد**: مسودة ← مرفوع ← معتمد (أو معاد بسبب)، ووكيل الجودة يعيد فتح المعتمد. عند الاعتماد يُولَّد PDF أفقي ويُحفظ في بنك
  الشواهد ويُربط بالمتطلب مع الشواهد الداعمة؛ و«أرشفة نسخة المتابعة» تضيف نسخة جديدة.
- **قاعدة قائمة**: `bash scripts/dev_setup.sh` يطبّق `db/migrations/002_forms.sql` تلقائياً.

## مطابقة قواعد النموذج الرسمي

- **التقييم الخارجي** حكم على صحة التقييم الذاتي: منطبق / غير منطبق / غير كافٍ.
- **المتحقق** = ذاتي «متحقق» وحكم «منطبق»؛ و«متحقق جزئي» لا يُحسب متحققاً.
- **لا ينطبق** مقبول فقط بشرط النجمة: (*) لقسم الدراسات العامة، (**) لأي قسم؛ والمنصة ترفضه خارج ذلك.
- **نسبة الاستيفاء** = المتحقق ÷ (المتطلبات − لا ينطبق المقبول).
- **مستوى الاجتياز** لكل معيار رئيسي: لا يقل أي قسم عن 89.5% في التقييم الخارجي.

## الواجهة الأمامية

ملفات ثابتة في `frontend/` بلا خطوة بناء ولا اعتماديات، يخدمها الـ API نفسه على `/app`
(وبالتالي تعمل داخل الشبكة المحلية دون أي CDN؛ خط IBM Plex Sans Arabic يُحمَّل من Google Fonts إن توفر، وإلا يُستخدم البديل).

- **التقديرات والشواهد**: لكل دور ما يخصه تلقائياً؛ المنسق يقدّر ويرفع الشواهد ويرفع للاعتماد، ورئيس القسم يعتمد أو يعيد بسبب،
  والمدقق يدخل التقييم الخارجي. التصفية "بانتظار إجرائي" تجمع ما ينتظر المستخدم الحالي.
- **لوحة المؤشرات** (وكيل الجودة والمدققون): خريطة الاستيفاء (كل مربع متطلب في قسم، قابل للنقر)، ملخص الأقسام،
  المعايير الرئيسية لكل قسم، أقوى وأضعف المعايير الفرعية، فجوة التقييم الذاتي، الإجراءات المتأخرة، وأزرار فتح الدورة وإغلاقها.

بيانات عرض تجريبية (4 أقسام × 48 متطلباً بنصوص تجريبية) لتجربة الواجهة أمام رؤساء الأقسام:

```bash
python scripts/seed_demo.py postgresql://aqap:aqap@localhost:5432/aqap_demo   # على قاعدة فارغة طُبّق عليها schema.sql
# حسابات العرض: dean@ynb · auditor@ynb · hod.cs@ynb · coord.cs@ynb · coord.ee@ynb · coord.me@ynb · coord.ad@ynb
```

## الاختبارات

```bash
pip install -r requirements.txt
AQAP_TEST_ADMIN_URL=postgresql://aqap:aqap@localhost:5432/postgres AQAP_TEST_XLSB=نموذج_العمل.xlsb pytest -q
```

تنشئ الاختبارات قاعدة `aqap_test` جديدة في كل تشغيل، وتستخدم تخزيناً محلياً بدل MinIO.

## مبادئ التصميم

- **قواعد العمل في قاعدة البيانات**: الانتقالات وتجميد الحقول وإغلاق الدورة تُفرض بدوال ومشغّلات PostgreSQL،
  والـ API يترجم رسائلها العربية إلى استجابة 409. لا توجد طريقة لتجاوزها من أي عميل.
- **معاملة واحدة لكل طلب** مع تمرير `aqap.user_id`، فيسجل `audit_log` هوية المنفّذ لكل تعديل.
- **نطاق الاطلاع**: المنحة بلا قسم تغطي كل الأقسام؛ الوصول خارج النطاق يعيد 404 لا 403 كي لا يكشف وجود السجل.
- **الشواهد**: الرفع يمر عبر الـ API (تحقق من النوع والحجم وحساب SHA-256)، ومفتاح التخزين لا يحمل اسم الملف،
  والتنزيل برابط موقّع قصير العمر بعد فحص الصلاحية ودرجة السرية، مع تسجيل كل تنزيل.
- **المصادقة**: HS256 للتطوير (`/api/v1/auth/dev-token`، معطّل في الإنتاج)، و JWKS/RS256 لمزوّد الدخول الموحّد.

## التقرير النهائي (`#/report`)

لوحة نتائج للقسم أو للكلية (متوسط الأقسام) بأساس احتساب: النتيجة النهائية أو التقييم الذاتي أو الخارجي.
- عدّاد لكل معيار رئيسي (أحمر < 50٪، وردي حتى حد الاجتياز 89.5٪، أخضر فوقه) ودائرة لكل معيار فرعي.
- أفضل خمسة وأضعف خمسة معايير فرعية، والنسبة العامة للعام التدريبي.
- جدولا أعداد المتطلبات (متحقق / غير متحقق / يحتاج تحسين) لكل معيار رئيسي وفرعي في كل قسم.
- «المتطلبات التي تتطلب خطة تحسينية» مع سبب الملاحظة: غير منفذ، أو منفذ جزئياً، أو الشاهد غير متوفر/غير كافٍ، أو خطة التحسين غير داعمة
  (`GET /cycles/{id}/reports/final-plans`). تتولد الخطة تلقائياً عند الاعتماد النهائي، ويشمل ذلك الآن المتطلب الذي لا يتوفر شاهده المطلوب
  (ترحيل `003_improvement_missing_evidence.sql`).

## نطاق المتطلبات (`#/scope`)

متطلب ليس من اختصاص قسم (مثل الإرشاد التدريبي أو المشروع لقسم الدراسات العامة) يستبعده وكيل الجودة من نطاق القسم بمسوّغ موثّق:
- لا يُولَّد له تقدير في الدورات الجديدة، ويُخفى من تقديرات القسم ومؤشراته والتقرير النهائي ونماذجه وخطط تحسينه، ولا يمنع إغلاق الدورة.
- يُصدَّر في النموذج الرسمي «لا ينطبق».
- يُفحص مقابل شرط النجمة في النموذج الرسمي؛ الاستبعاد خارج الشرط يتطلب تأكيداً صريحاً ويُعلَّم «خارج شرط النجمة».
- القرار يُلغى ولا يُحذف (سجل تدقيق)، ولا يغيّر نتائج دورة مغلقة. الإعادة للنطاق تولّد التقدير في الدورة المفتوحة.
- واجهات: `GET /departments/{id}/applicability`، `POST …/applicability/exclusions`، `DELETE …/applicability/exclusions/{requirement_id}` (ترحيل `004_requirement_exclusion.sql`).

## تقويم الإنجاز (`#/calendar`)

يرفع وكيل الجودة مواعيد إنجاز المعايير الفرعية أو المتطلبات (لكل الأقسام أو لقسم بعينه)، إدخالاً مباشراً أو برفع ملف Excel/CSV من القالب:
- القالب (`GET /cycles/{id}/calendar/template`) صف لكل معيار فرعي: الرمز، الاسم، تاريخ البدء، تاريخ الانتهاء، رمز القسم (فارغ = كل الأقسام)، ملاحظات. يمكن إضافة صفوف لمتطلبات بعينها.
- الاستيراد (`POST /cycles/{id}/calendar/import`) يقبل ‎.csv و ‎.xlsx، ويحدّث الموعد إن وُجد، ويُرجع أخطاء الصفوف دون إيقاف البقية.
- الموعد الأخص يغلب: المتطلب على المعيار الفرعي، والقسم على «كل الأقسام».
- الإنجاز = تقديرات النطاق المرفوعة من القسم فما بعدها ÷ تقديرات النطاق؛ الحالة: منجز / يقترب (7 أيام) / متأخر / قادم.
- يظهر الموعد بجانب كل متطلب في «التقديرات والشواهد» (باقي/متأخر بالأيام). ترحيل `006_calendar.sql`.
